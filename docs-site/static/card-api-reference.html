Card Service API Reference

ISO 8583 card processing, card lifecycle management, fraud engine, token vault, settlement, and BaaS card API.
Base URL: http://localhost:8081 · Card Open Banking: /card-api/v1/

Overview

The card-service is a standalone Spring Boot microservice (port 8081) that owns all card domain data. It works alongside the fep-service (ISO 8583 TCP server on port 8583) and the backend monolith (port 8080).

Architecture

[POS / ATM Terminal]
      ↓  ISO 8583 over TCP (port 8583)
[fep-service]  ──REST──▶  [card-service :8081]  ──REST──▶  [backend :8080]
                              Card lifecycle                Account balances
                              Fraud engine                  Transaction posting
                              Token vault, settlement

Card Lifecycle

Virtual card:

ISSUED→ ACTIVE⇄ BLOCKED→ EXPIRED→ CANCELLED

Physical card:

ORDERED→ PRODUCED→ DISPATCHED→ ACTIVATION_PENDING→ ACTIVE⇄ BLOCKED

Authentication

Card-service supports three authentication modes depending on the endpoint group:

Endpoint GroupAuth MethodHeader
/3ds/acs/**None (Directory Server mTLS in prod)—
/api/v1/internal/**JWT with realm role FEP_SERVICE — fep-service only (Keycloak client cba-fep-service, client_credentials). Any other token → 403, none → 401. Also never routed by the public ingress (cont. 34)Authorization: Bearer {jwt}
/api/v1/**JWT (Keycloak realm cba)Authorization: Bearer {jwt}
/card-api/v1/**JWT or API Key (dual-mode)Authorization: Bearer {jwt} or Authorization: ApiKey cba_{key}

DPoP is not supported. A request whose Authorization header uses the DPoP scheme is rejected on every path with 401 and error code DPOP_NOT_SUPPORTED, before any security chain runs — a compensating control for CVE-2026-41707 (Spring Security 6.5 DPoP replay cache; fixed only in Spring Security 7).

RBAC Roles

Roles come from the Keycloak token's realm_access.roles claim; each role R becomes the authority ROLE_R (the principal name stays sub). A token without the required role gets 403 with error code ACCESS_DENIED. API_KEY is not a Keycloak role: it is granted to requests that authenticate with Authorization: ApiKey cba_{key}.

RoleAccess Level
ADMINFull card-service access including fraud rule management, settlement, bureau
TELLERCard operations: block/unblock, dispute raising, settlement view
CUSTOMERNo card-service access yet: card endpoints accept CUSTOMER only once card ownership checks exist
API_KEYM2M BaaS integrator — card issuance, analytics, webhooks

POST /api/v1/cards/{id}/wallet/loads Load a prepaid wallet (backlog 15c)

ADMIN, TELLER. Moves money from the cardholder's backend account into the wallet; the backend debits the account and posts DR deposit / CR 2500 Prepaid Card Liabilities. The movement is claimed first (PENDING), the backend is called, then the answer is written: 201 COMPLETED (wallet credited), 202 PENDING (no answer — retried every minute with the same reference until answered; never failed automatically), 400 with the backend's reason (INSUFFICIENT_FUNDS, ACCOUNT_NOT_FOUND, CURRENCY_MISMATCH, ACCOUNT_NOT_ACTIVE, …; the movement is kept FAILED). A card's first load opens its wallet in currencyCode (required then: 400 CURRENCY_REQUIRED); later loads must be in the wallet's currency. Also 400 NOT_A_PREPAID_CARD, CARD_NOT_LOADABLE (cancelled/expired), INVALID_AMOUNT.

{ "sourceAccountId": "…", "amount": 100.00, "currencyCode": "USD" }

Response (201 / 202)

{ "data": { "id": "…", "cardId": "…", "movementType": "LOAD", "reference": "WLD-…", "accountId": "…",
  "amount": 100.00, "currencyCode": "USD", "status": "COMPLETED", "failureReason": null, "attempts": 0 }, "errors": [] }
POST /api/v1/cards/{id}/wallet/unloads Redeem a prepaid wallet to the customer's account

ADMIN, TELLER. Body { "destinationAccountId", "amount" }. The amount leaves the wallet first (so card spend can't use it in flight); the backend credits the account and posts DR 2500 / CR deposit. A refusal gives the amount back to the wallet. 400 INSUFFICIENT_WALLET_BALANCE, NO_WALLET. Same 201/202/400 answers as a load.

GET /api/v1/cards/{id}/wallet Prepaid wallet and its movements

ADMIN, TELLER. { cardId, walletId, balance, currencyCode, status, movements[] } — the last 50 loads/unloads, newest first; walletId null until the first load. GET /api/v1/cards/wallets/totals (ADMIN, CARD_READER) returns balances per currency, which the backend's opening-balances?scope=PREPAID reconciles against GL 2500.

Prepaid spend (backlog 15c, D5a): approval decrements the wallet (the hold) and adds a PENDING settlement item under a PPD- reference; batch close clears it on the backend (POST /api/v1/card-prepaid/clearings: DR 2500 / CR 2300, with interchange — prepaid now earns like debit — and scheme fees), so it enters the scheme report's expected net. A reversal before clearing gives the wallet back; after clearing the backend refunds first (pro rata, once), then the wallet is credited — unreachable → RC 96. An item still uncleared after 7 days is FAILED and its wallet decrement given back. A card never loaded declines RC 51 (was 91).

GET /api/v1/cards/{id}/authorizations Authorization history for a card

Approved and declined authorizations, newest first. The backend's Open Banking layer maps these to OB transactions (GET /open-banking/v3.1/aisp/accounts/{cardId}/transactions). The backend had always called this path; until it existed, card transactions were empty.

Authorization (Internal)

Called by fep-service for every 0100/0200 ISO 8583 message. Not intended for external integrators.

Auth (cont. 34): every /api/v1/internal/** endpoint (/authorize, /advise, /reverse, /detokenize) requires a JWT with realm role FEP_SERVICE, held only by Keycloak client cba-fep-service's service account. No token → 401; ADMIN/TELLER/CUSTOMER/CARD_READER → 403. They had been open on the assumption of network isolation the k8s ingress never gave. The unused GET /api/v1/internal/cards/{cardId}/authorizations was removed (history: GET /api/v1/cards/{id}/authorizations). An unknown card now declines with RC 14 (it was a 500, and its log row was rolled back).
Funds check (cont. 35): amount is DE4, minor units of the DE49 currency (2500 = 25.00 USD; 0 decimals for JPY, 3 for KWD). It is converted to major units before it's compared with the balance. Until cont. 35 it was compared raw, so 25.00 against a 500.00 balance declined.
  • DEBIT: the backend's GET /api/v1/accounts/{id}/balance (service token, client cba-card-service, role CARD_SERVICE).
    • 51 insufficient funds.
    • 57 when the account can't be debited (frozen, dormant, lock-in) or the transaction currency differs from the account's (no FX on the authorization path).
    • 91 when the backend can't be reached.
  • PREPAID: the same units and currency rules against the wallet.
  • CREDIT: 57. The backend has no revolving credit line yet, so there's nothing to authorize against.
  • Balance inquiry (processing code 310000) returns the available balance in major units and reserves nothing.
  • Approvals reserve funds.
    • Debit: an atomic backend hold (POST /api/v1/accounts/{id}/card-holds, keyed by a SHA-256 of card, STAN, RRN, terminal, amount and currency, so a retried 0100 doesn't hold twice and a different authorization can't reuse another's hold; a reused key with another amount declines 94). It expires after 7 days. If card-service's transaction rolls back after the hold was placed, the hold is released.
    • Prepaid: the wallet is decremented under a row lock.
    • A reversal (/reverse, 0400/0420) of an approved authorization releases the hold or restores the wallet, once. If the backend can't be reached to release the hold, the reversal answers 96 and is not recorded, so the network's retry releases it.
    • A reversal (full or partial) of a purchase that batch close is clearing at that moment answers 96 and is not recorded; the network's retry, once the capture has landed, refunds the reversal amount through the backend. A full reversal the backend refuses (13) or can't be reached for (96) leaves the purchase to clear as before.
    Until cont. 35, approvals reserved nothing, so any number could pass against the same balance. Authorization-history responses carry the reservation as holdReference / walletDebit. Clearing (taking the money) and the GL for card spend are still to come.

Foreign-currency transactions (backlog 17). When the scheme sends the cardholder billing amount (DE6) and its currency (DE51), the card's money moves in them: the backend hold or 0200 debit, the prepaid wallet, interchange quotes and the settlement item are all in DE6/DE51, so a EUR purchase on a USD account approves for its USD amount. DE4/DE49 stay on the authorization log as the merchant's transaction (and drive the fraud rules). RC 30 (checked before fraud scoring) for: DE6 without DE51 or the reverse; DE6 not a positive whole number; DE6 without DE10; DE6 more than 1% from DE4 × DE10 (between the two currencies' minor units); DE51 equal to DE49 with DE6 ≠ DE4. The fraud single-amount limit checks both DE4/DE49 and DE6/DE51 — either over its limit triggers. Without DE6, a transaction in another currency than the account still declines RC 57. The scheme is taken to settle in the billing currency. POST /api/v1/internal/reverse also takes optional billingAmount/billingCurrencyCode: a reversal gives back that DE6 (never more than the original moved), or DE4 pro-rated onto the original's DE6 (HALF_UP); a DE51 that isn't the original's card currency → RC 13.

Settlement

Dual-message settlement batches. Authorizations are held pending until end-of-day batch close (nightly at 23:58). Single-message (real-time) transactions bypass batching.

Dual-Message Flow

0100 Auth Request → 0110 Auth Response (backend hold; settlement item PENDING)
     ↓ (batch close, nightly 23:57 or manual)
backend POST /api/v1/accounts/{id}/card-holds/{ref}/capture → debit + DR deposit / CR 2300
     + interchange earned DR 2300 / CR 4005, scheme fees DR 5006 / CR 2300 → item SETTLED (glNet)
0200 Financial Request (ATM cash) → backend POST …/card-debits at once (interchange paid DR 5007 / CR 2300) → item SETTLED
0400 Reversal → backend …/release (hold released, or completed debit refunded with fees reversed pro rata) → item REVERSED
next day: operations record each scheme's settlement report → backend POST /api/v1/card-settlements
     DR 2300 / CR 1003 → batch SETTLED

There is no scheme clearing-file intake yet: batch close presents each purchase at its authorized amount. Interchange and scheme fees (backlog 15b) are quoted when an item is claimed for clearing — the issuer earns interchange on a purchase and pays it on ATM cash at another bank's machine; scheme fees are assessment + network only (cross-border needs the merchant's country, backlog 15d); prepaid gets none until it has a GL (15c). They are sent with the capture and post in its journal; each item keeps the figures the backend posted and glNet — what the bank owes the scheme for it (minor units: amount − interchange earned + interchange paid + fees). A refund records refundGlNet on the day it happens.

POST /api/v1/cards/settlement/batches/{id}/close Close an open settlement batch

Clears each PENDING debit-card item on the backend (…/card-holds/{ref}/capture: the hold becomes a debit and DR deposit / CR 2300 Card Scheme Settlement Payable posts, with the item's interchange and scheme fees). The figures are quoted once, when the item is claimed; a retried close reuses them. Refused items (e.g. a late presentment without funds) become FAILED with failureReason — never force-posted. Prepaid and 0200 items are already completed. The batch ends CLOSED, which the nightly scheme file export (23:58) picks up; if the backend can't be reached the batch stays OPEN and the next close retries (clearing is idempotent). Items now carry cardId, accountId, cardType, holdReference, failureReason, clearedAt.

// Response (200)
{ "data": { "id": "...", "status": "CLOSED", "totalAmount": 1250000,
  "itemCount": 47, "closedAt": "2026-01-15T23:58:00Z" } }
POST /api/v1/cards/settlement/scheme-reports Record a scheme settlement report (the cash leg)

Operations enter the net a card scheme reports for one settlement date and currency (ADMIN). The expected net is the glNet of that date's cleared items plus the refundGlNet of that date's refunds, for the scheme and currency. card-service sends the reported and the expected net to the backend (POST /api/v1/card-settlements with amount and expectedAmount); the backend, which owns the GL, decides on any difference (backlog 15d). Equal figures post DR 2300 / CR 1003 Card Scheme Settlement Account (negative net: the reverse). A difference within the currency's tolerance (backend app.cards.settlement.difference-tolerance, default 0) is recorded: 2300 at the expected net, 1003 at the reported net, the rest to GL 1004 Card Settlement Differences; the report keeps its difference. Either way the date's batches become SETTLED once all their GL items are in recorded reports. Above the tolerance the backend refuses: recorded=false, reason=DIFFERENCE_OVER_TOLERANCE with expectedNet, reportedNet and difference — the report row is deleted and its items un-stamped, so nothing is kept and operations can record a corrected figure. (Until cont. 61 card-service refused any mismatch itself with AMOUNT_MISMATCH.) Any other backend refusal is returned the same way. Other refusals: DATE_NOT_CLOSED (the date must be before today), BATCH_NOT_CLOSED (a batch of the date still OPEN, or items PENDING/CLEARING), ALREADY_RECORDED (another amount after recording), REPORT_IN_PROGRESS, UNKNOWN_CURRENCY, INVALID_AMOUNT. The same report again: recorded=true, repeat=true, nothing posted. Backend unreachable → BACKEND_UNAVAILABLE; the report stays POSTING and recording it again finishes it with the same backend reference. Expected net 0 and reported 0 → recorded with no journal (expected 0 with a reported figure goes to the backend).

// Request — netAmount major units, signed (+ = the bank pays the scheme); currency alphabetic or numeric

Settlement File Export

Pluggable scheme file exporters. Each scheme has its own file format (Visa BASE II, Mastercard IPM, Verve NIBSS, Afrigo PAPSS, UnionPay CUPS). Exporters are disabled by default — flip enabled: true and supply credentials in application.yml to activate at production.

Issuer or acquirer (backlog 21). These five formats are acquirer presentments: the acquirer submits clearing records, the issuer receives them and sends back chargebacks and fee collections. This platform issues cards, so card.settlement.export.role defaults to ISSUER and nothing is exported — the nightly run and the retry poller do nothing and a manual export answers 409 PRESENTMENT_REQUIRES_ACQUIRER_ROLE, whatever a scheme's enabled says. Set ACQUIRER only for an acquiring business with its own transactions.

Amounts in every file are whole ISO 4217 minor units (DE4), the same unit in data records and trailer totals; a fractional or over-wide amount, or a record without a currency, fails the file instead of being written. Nightly (export-cron): CLOSED or SETTLED batches from the last lookback-days (7) under their own settlement date, first attempts only. Retries are scheduled, never slept: a failed send goes back to PENDING with nextRetryAt (+retry-delay-seconds) and the poller (retry-poll-ms) sends it again, up to max-retries, then FAILED. Transmission statuses: PENDING → SENDING → TRANSMITTED (→ ACKNOWLEDGED) or FAILED. One live transmission per batch + scheme (unique index); a send stuck in SENDING past sending-lease-minutes becomes FAILED ("INTERRUPTED") and is never resent automatically — confirm with the scheme, then export again by hand.

Interchange Management

Per-scheme interchange rate tables and scheme assessment fees. The InterchangeQualificationEngine determines the applicable rate based on scheme + card type + MCC + transaction type + channel, from the issuer's side (backlog 15b): a purchase earns interchange, cash at another bank's ATM pays it, and the scheme's fees are paid either way. The channel comes from the DE22 entry mode (05x chip, 07x contactless, 02x/90x magstripe = card present; 01x manual, 81x e-commerce = card not present). Scheme fees (backlog 15d, decision D2a): ASSESSMENT and NETWORK on every transaction; CROSS_BORDER when the acquirer's country (DE19, ISO 3166 numeric, stored as authorization_log.acquiring_country) isn't the card's home country (its BIN range's country_code) — none when either is missing or unknown, and the settlement item is flagged countryUnknown (authorizations logged before V20 have no DE19); INTERNATIONAL_SERVICE (currency conversion) when the transaction currency (DE49) isn't the card's currency (DE51). All are charges the scheme makes to the bank — part of schemeFeeAmount, which the backend posts DR 5006 / CR 2300 (no backend change) — never passed to the cardholder. Percentages apply to the card amount (DE6 when sent, else DE4); fee groups are rounded separately so the parts add up to the total. fixedFee is in major units of the row's currencyCode (ISO 4217 alphabetic) and applies only to transactions in that currency; interchange is rounded once to the currency's digits. Scheme UNIONPAY is canonical (UNION_PAY is accepted and stored as UNIONPAY). GET /api/v1/interchange/calculate?authId= returns {interchangeAmount, schemeFeeAmount, netSettlementAmount, rateApplied, direction, crossBorderFee, currencyFee, countryUnknown} in major units — netSettlementAmount is what the issuer owes the scheme; crossBorderFee and currencyFee are the parts of schemeFeeAmount. Settlement items (GET …/batches/{id}/items) carry the same split in minor units (crossBorderFee, currencyFee, countryUnknown), and authorization log entries carry acquiringCountry. Scheme fees take an optional currencyCode (default USD).

Card Controls

Card controls take an API key or an ADMIN/TELLER token (customer tokens aren't admitted: card-service has no customer ownership check). Controls are freeze/unfreeze, the contactless, card-not-present and international switches, and PIN change via HSM.

// Request — every field optional; one left out is unchanged
{

  "contactlessEnabled": true,
  "cnpEnabled": false,
  "internationalEnabled": true

// Response (200) — the card, with its switches
{ "data": { "id": "…", "status": "ACTIVE", "contactlessEnabled": true, "cnpEnabled": false,
            "internationalEnabled": true, … }, "meta": {}, "errors": [] }

The switches are stored on the card (default on) and enforced at authorization, before any funds are reserved. A switched-off channel declines with RC 57 (transaction not permitted to cardholder); reversals (0400) are never blocked.

Switch offDeclined when
contactlessEnabledDE22 starts 07 (contactless chip) or 91 (contactless magstripe)
cnpEnabledDE22 isn't card present — card present is 02, 05, 07, 80, 90, 91; manual entry 01, e-commerce 81 and a missing DE22 are not
internationalEnabledthe acquirer's country (DE19, ISO 3166 numeric) isn't the card's home country (its BIN range's country_code). Fails closed: a request without DE19, or with a code that isn't ISO 3166, is declined too
