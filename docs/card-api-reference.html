Card Service API Reference

ISO 8583 card processing, card lifecycle management, fraud engine, token vault, settlement, and BaaS card API.
Base URL: http://localhost:8081 · Card Open Banking: /card-api/v1/

Overview

The card-service is a standalone Spring Boot microservice (port 8081) that owns all card domain data. It works alongside the fep-service (ISO 8583 TCP server on port 8583) and the backend monolith (port 8080).

Architecture

[POS / ATM Terminal]
      ↓  ISO 8583 over TCP (port 8583)
[fep-service]  ──REST──▶  [card-service :8081]  ──REST──▶  [backend :8080]
                              Card lifecycle                Account balances
                              Fraud engine                  Transaction posting
                              Token vault, settlement

Response Envelope

All card-service REST endpoints return the standard CBA response envelope:

{
  "data": { ... },
  "meta": { "page": 0, "size": 20, "total": 150 },
  "errors": []
}

Error Format

{
  "data": null,
  "meta": {},
  "errors": [{ "code": "CARD_NOT_FOUND", "message": "Card abc123 not found", "field": null }]
}

Card Lifecycle

Virtual card:

ISSUED→ ACTIVE⇄ BLOCKED→ EXPIRED→ CANCELLED

Physical card:

ORDERED→ PRODUCED→ DISPATCHED→ ACTIVATION_PENDING→ ACTIVE⇄ BLOCKED

Cards

Card lifecycle management — issue, block, activate, cancel, replace. Card entities are linked to a bank account, loan (credit card), or prepaid wallet.

  "virtualFlag": false, "customerId": "...", "linkedEntityId": "..." }],

Request Body

GET /api/v1/cards/{id}/balance Available balance for a card

Returns available balance in minor units. Debit/prepaid reads wallet balance; credit reads creditLimit − outstandingBalance.

Response (200)

{ "data": { "availableBalance": 250000, "cardType": "DEBIT", "currency": "840" }, "errors": [] }

Fraud Rules

Rule-based fraud engine with configurable weights (0–100). Hard-block rules (CARD_EXPIRED, CARD_BLOCKED, PIN_RETRY_EXCEEDED) always have weight 100 and short-circuit evaluation.

Score Thresholds

Score RangeDecisionDE39 Response Code
0–29APPROVE00
30–69STEP_UP (force online PIN)0110 with PIN required
70–100DECLINE05 / 62
PUT /api/v1/cards/fraud/rules/{id} Update rule weight and parameters

Request Body

{
  "weight": 45,
  "enabled": true,
  "params": {
    "thresholds": { "840": 100000, "404": 13000000 },
    "default_threshold_minor_units": 100000
  }
}
Currency thresholds in params.thresholds use ISO 4217 numeric codes as keys. Always include a default_threshold_minor_units fallback.

Token Vault

Simulated EMVCo TSP — maps real PANs to Device PANs (DPANs). DPAN BIN prefix is 9999xx. FEP detects token BIN and calls /tokens/detokenize before authorization lookup.

// Response (201)

  "tokenRef": "tok_abc123", "status": "ACTIVE" }, "errors": [] }

BIN Management

Manages BIN (Bank Identification Number) ranges for scheme routing. Supports both 6-digit (legacy) and 8-digit BINs (EMV 2019 mandate). FEP calls /api/v1/bins/{bin}/scheme to route messages to the correct scheme adapter.

POST /api/v1/bins Register a BIN range 
// Request
{
  "binStart": "41111100",         // 6 or 8 digits
  "binEnd":   "41111199",
  "scheme": "VISA",               // VISA | MASTERCARD | VERVE | AFRIGO | UNION_PAY
  "cardType": "DEBIT",
  "productType": "CLASSIC",
  "countryCode": "US",
  "currencyCode": "840"
}

// Response (201)
{ "data": { "id": "...", "binStart": "41111100", "scheme": "VISA", "active": true } }

Settlement

Dual-message settlement batches. Authorizations are held pending until end-of-day batch close (nightly at 23:58). Single-message (real-time) transactions bypass batching.

Dual-Message Flow

0100 Auth Request → 0110 Auth Response (hold funds)
     ↓ (end of day)
0320 Batch Upload → 0322 Batch Advice → 0324 Batch Close → GL posting
POST /api/v1/cards/settlement/batches/{id}/close Close an open settlement batch

Closing a batch triggers scheme file export (if configured) and final GL debit/credit entries via the monolith backend.

// Response (200)
{ "data": { "id": "...", "status": "CLOSED", "totalAmount": 1250000,
  "itemCount": 47, "closedAt": "2026-01-15T23:58:00Z" } }

Settlement File Export

Pluggable scheme file exporters. Each scheme has its own file format (Visa BASE II, Mastercard IPM, Verve NIBSS, Afrigo PAPSS, UnionPay CUPS). Exporters are disabled by default — flip enabled: true and supply credentials in application.yml to activate at production.

POST /api/v1/cards/settlement/export/{batchId} Manually trigger scheme file export for a batch

Query Parameters

ParamDescription
settlementDateOverride date (YYYY-MM-DD). Defaults to batch date.

Disputes & Chargebacks

Scheme-compliant chargeback workflow. Supports Visa, Mastercard, Verve, Afrigo, and UnionPay reason codes with enforced processing timeframes.

State Machine

RAISED→ RETRIEVAL_REQUESTED→ CHARGEBACK_INITIATED→ REPRESENTMENT→ PRE_ARBITRATION→ RESOLVED
A nightly scheduled job (ChargebackTimeframeEnforcer) auto-expires retrieval requests and auto-accepts lapsed representments per scheme deadlines.
POST /api/v1/cards/disputes Raise a new dispute 
{
  "cardId": "uuid",
  "transactionRef": "123456789012",   // RRN (DE37) of disputed transaction
  "disputeReason": "UNAUTHORIZED",    // UNAUTHORIZED | GOODS_NOT_RECEIVED | DUPLICATE | AMOUNT_MISMATCH | OTHER
  "originalAmount": 5000,
  "raisedBy": "customer-uuid"
}
POST /api/v1/cards/disputes/{id}/chargeback Initiate formal chargeback 
{ "reasonCodeId": "uuid" }   // From /api/v1/cards/disputes/reason-codes
Valid from RAISED (skip retrieval) or RETRIEVAL_REQUESTED (after docs obtained). The chargeback deadline is set from the reason code's maxDaysToRespond.

Card Personalization Bureau

Physical card issuance requires EMV chip personalization via a certified bureau (Thales, HID Global, Idemia). The bureau module manages the CDP (Card Data Preparation) lifecycle and progresses card status from ORDERED → PRODUCED → DISPATCHED.

Bureau Job Lifecycle

PENDING→ SENT→ CONFIRMED→ FAILED
POST /api/v1/bureau/jobs Create bureau batch from all ORDERED cards

Collects all cards in ORDERED status and creates a batch job. Returns the job with all items.

// Response (201)
{ "data": { "id": "...", "batchRef": "CBA-2026-01-15-001",
  "cardCount": 12, "status": "PENDING", "submittedAt": null } }

3D Secure ACS

Access Control Server for card-not-present authentication. Receives authentication requests (AReq) from scheme Directory Servers, performs risk-based frictionless flow or OTP challenge, and returns ARes with CAVV.

3DS endpoints are not JWT-protected — they are called by scheme Directory Servers (mTLS in production) and by cardholder browsers. In staging/dev, they are open.
POST /3ds/acs/areq Receive authentication request from Directory Server 
// AReq (sent by Directory Server)
{
  "threeDSServerTransID": "uuid",
  "dsTransID": "uuid",
  "acsTransID": "uuid",
  "messageVersion": "2.3.1",
  "pan": "4111111111111111",
  "cardExpiryDate": "2811",
  "purchaseAmount": "5000",
  "purchaseCurrency": "840",
  "merchantName": "PayOnline Ltd",
  "notificationURL": "https://ds.example.com/notify"
}

// ARes — frictionless
{ "acsTransID": "...", "transStatus": "Y",
  "authenticationValue": "CAVV_HEX", "eci": "05" }

// ARes — challenge required
{ "acsTransID": "...", "transStatus": "C",
  "acsURL": "https://acs.cba.com/3ds/acs/challenge/{acsTransId}" }

API Key Management

API keys are hashed with SHA-256 and stored in the api_keys table. The raw key value is shown exactly once on creation and cannot be retrieved again.

// Response (201) — rawKey shown ONCE, store it immediately
{ "data": { "id": "...", "name": "Fintech Partner A",
  "rawKey": "cba_a1b2c3d4e5f6...",    // only time this appears
  "scopes": ["CARD_READ", "CARD_ISSUE"], "createdAt": "..." } }

Card Controls (Consent-gated)

Customer card controls require FAPI 2.0 consent or an API key. Controls include freeze/unfreeze, enabling/disabling contactless/CNP transactions, and PIN change via HSM.

PUT /card-api/v1/cards/{id}/controls Update card controls (freeze, contactless, CNP, international) 
{
  "frozen": false,
  "contactlessEnabled": true,
  "cnpEnabled": false,
  "internationalEnabled": true
}
POST /card-api/v1/cards/{id}/pin/change Change PIN (routed through HSM) 
{ "oldPinBlock": "...", "newPinBlock": "..." }  // ISO-0 format
HSM verifies old PIN using IBM 3624 (CA command) or Visa PVV (DC command) before setting the new PIN offset (A2 command).

Webhooks

Register callback URLs to receive real-time card events. Delivery is async via Spring @Async WebClient with HMAC-SHA256 payload signing. Exponential backoff: 15 s → 60 s → 5 min → 30 min → 2 h (5 attempts).

Signature Verification

X-CBA-Signature: sha256={HMAC-SHA256(payload, secret)}
X-CBA-Event: AUTHORIZATION.APPROVED
X-CBA-Delivery: {uuid}

Event Catalogue

EventTrigger
AUTHORIZATION.APPROVEDAuth approved by fraud engine + balance check
AUTHORIZATION.DECLINEDAuth declined (insufficient funds, fraud, blocked)
AUTHORIZATION.REVERSEDReversal processed (MTI 0400)
CARD.ISSUEDNew card created
CARD.ACTIVATEDCard moved to ACTIVE
CARD.BLOCKEDCard blocked
CARD.UNBLOCKEDCard unblocked
CARD.EXPIREDCard reached expiry (nightly CoB job)
CARD.PIN_CHANGEDPIN changed via HSM
CARD.LIMIT_CHANGEDAny spending limit updated
FRAUD.RULE_TRIGGEREDAny fraud rule score > 0
FRAUD.CARD_STEP_UPScore 30–69; contactless step-up to online PIN
FRAUD.CARD_DECLINED_HIGH_RISKScore ≥ 70
DISPUTE.RAISEDNew dispute created
DISPUTE.RESOLVEDDispute resolved (ISSUER or ACQUIRER favor)
